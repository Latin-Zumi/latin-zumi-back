# Spec: 404 con contexto y sin stack en logs

## Fecha
2026-11-04

## Orden de ejecución: 049

## Problema

Render registra repetidamente:

```text
AppError: Ruta no encontrada
  at file:///opt/render/project/src/dist/server.js:44:10
  ...
{ statusCode: 404, code: 'NOT_FOUND', isOperational: true }
```

El origen es el fallback de `src/server.ts`, que ejecuta
`next(new AppError('Ruta no encontrada', 404))` cuando ningún router coincide
con el método y la ruta solicitados. No es un crash: es la respuesta correcta
para una ruta no registrada.

La causa del ruido está en `src/middleware/errorHandler.ts`: hace
`console.log(err)` para todo error, incluidos los `404` operativos, y el log no
incluye método ni ruta. Por eso no se puede saber qué cliente está llamando a
una ruta inexistente.

Alcance: corregir el diagnóstico y el nivel de log de los `404`. No se agregan
rutas nuevas ni se cambia el contrato HTTP, porque la ruta concreta que genera
los `404` no se puede identificar con la información actual.

## Solución propuesta

En `errorHandler`, reemplazar el `console.log(err)` incondicional por un log
según el estado resuelto:

- `4xx` operativos: una línea `warn` con estado, código, método y pathname. Sin
  stack.
- `5xx` o errores no operativos: `console.error` con el error completo y stack.

El pathname se obtiene de `req.originalUrl` quitando el query string, para no
registrar tokens ni datos sensibles. No se registra body ni headers.

La respuesta HTTP no cambia: el `404` sigue siendo
`{ "code": "NOT_FOUND", "message": "Ruta no encontrada" }` y el resto de
códigos conserva su contrato actual.

### Log del 404

`errorHandler` se ejecuta después del fallback de `src/server.ts` y recibe el
`AppError` junto con el `Request`. Debe emitir una sola línea y no imprimir el
stack.

```ts
const pathname = req.originalUrl.split('?')[0];

if (status >= 500) {
  console.error(`[${status}] ${req.method} ${pathname}`, err);
} else {
  console.warn(`[${status}] ${err.code ?? 'ERROR'} ${req.method} ${pathname}`);
}
```

Resultado: ante `GET /ruta-inexistente?token=abc` se registra
`[404] NOT_FOUND GET /ruta-inexistente`. El query string queda fuera del log.

### Respuesta sin cambios

El fallback sigue creando el mismo error operativo. Lo único que cambia es cómo
se registra.

```ts
app.use((_req: Request, _res: Response, next: NextFunction) => {
  next(new AppError('Ruta no encontrada', 404));
});
```

Resultado: el cliente recibe el mismo `404` JSON; el operador obtiene método y
ruta para identificar al llamador.

### Prueba del handler

El test monta una app Express mínima, registra una ruta que lanza el error y
verifica estado, body y llamadas a `console.warn`/`console.error`.

```ts
app.get('/boom', () => {
  throw new AppError('Ruta no encontrada', 404);
});
app.use(errorHandler);

const response = await fetch(`${baseUrl}/boom?token=abc`);
expect(response.status).toBe(404);
expect(await response.json()).toEqual({
  code: 'NOT_FOUND',
  message: 'Ruta no encontrada',
});
expect(warn).toHaveBeenCalledWith('[404] NOT_FOUND GET /boom');
expect(error).not.toHaveBeenCalled();
```

## Pasos

1. Extraer en `errorHandler` el estado HTTP resuelto para cada tipo de error ya
   soportado: `AppError`, JSON inválido, payload grande, `23505` y `23503`; el
   resto es `500`.
2. Loguear `4xx` con `console.warn` en una línea con estado, código, método y
   pathname sin query string.
3. Mantener `console.error` con el error y su stack para `5xx` y errores no
   operativos.
4. No modificar el orden de middlewares, las rutas, CORS ni los bodies de
   respuesta.
5. Agregar el test del handler con un servidor HTTP efímero, siguiendo el patrón
   de `src/tests/routes/*.test.ts`.

## Cómo probar

- [x] `GET /ruta-inexistente` responde `404` con `{ code: 'NOT_FOUND', message: 'Ruta no encontrada' }` y genera una línea `warn` con método y ruta.
- [x] `GET /ruta-inexistente?token=abc` no incluye `token=abc` en el log.
- [x] Un error `500` sigue generando `console.error` con stack y responde
      `{ code: 'INTERNAL_ERROR', message: 'Error interno del servidor' }`.
- [x] JSON inválido sigue respondiendo `400 INVALID_JSON`; payload mayor a
      100 KB sigue respondiendo `413 PAYLOAD_TOO_LARGE`.
- [x] Violaciones `23505` y `23503` siguen respondiendo
      `400 DUPLICATE_VALUE` e `400 INVALID_REFERENCE`.
- [ ] `npm test` pasa. (Falla preexistente en `src/tests/config/env.test.ts` por
      el default de `EMAIL_FROM`; ajeno al spec 049.)

## Riesgos / notas

- Este cambio no elimina los `404` de clientes que llaman rutas inexistentes:
  los hace diagnosticables. Si el nuevo log revela una ruta legítima del
  frontend, agregarla requiere otro cambio.
- Los escaneos automatizados seguirán generando una línea de log por request;
  muestreo o deduplicación quedan fuera de alcance.
- No registrar query string, body ni headers evita filtrar credenciales o
  tokens de recuperación.
