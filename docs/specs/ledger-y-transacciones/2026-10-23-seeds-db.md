# Spec: Seeds de datos para probar la DB

## Fecha
2026-10-23

## Orden de ejecución: 002

## Problema
La base tiene un esquema de ledger, pero no hay datos de ejemplo ni un flujo definido para cargarlos. Esto dificulta probar consultas y revisar los saldos sin insertar registros manualmente.

## Solución propuesta
Agregar seeds de demostración en `db/seeds/` y un comando ejecutable que los cargue después de inicializar el esquema. Los datos incluirán cuentas y transacciones balanceadas con sus entries, usando identificadores e idempotency keys estables para que volver a ejecutar el seed no duplique datos. La carga debe respetar las restricciones del ledger y dejar los saldos consultables en `account_balances`.

## Archivos afectados
- db/seeds/ (datos de demostración)
- db/scripts/ (ejecutor de seeds)
- package.json (comando para ejecutar seeds)
- db/README.md (instrucciones de uso)

## Pasos
1. Definir un conjunto pequeño de cuentas de prueba en más de una moneda.
2. Crear transacciones balanceadas de ejemplo con sus entries, usando claves estables para permitir ejecuciones repetidas.
3. Implementar un ejecutor que lea los archivos de `db/seeds/` y los aplique a la conexión configurada por variables `DB_*`.
4. Agregar un comando npm y documentar el orden de uso: inicializar el esquema y luego cargar seeds.

## Cómo probar
- [ ] Inicializar el esquema y cargar seeds con el comando documentado.
- [ ] Consultar `account_balances` y verificar que aparecen los saldos de ejemplo esperados.
- [ ] Ejecutar seeds dos veces y verificar que no se duplican cuentas, transacciones ni entries.

## Riesgos / notas
- Los seeds deben insertar transacciones balanceadas por moneda para satisfacer el trigger diferido del ledger.
- Las reglas de inmutabilidad de `entries` implican que el seed debe ser aditivo e idempotente; no debe limpiar datos existentes.
- Se asume que la base ya fue creada y que `db/migrations/001_ledger.sql` fue aplicada mediante el inicializador existente.
